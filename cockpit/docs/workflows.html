Cockpit, step by step

One chat-style app for tasks, habits, contacts and home upkeep. Each workflow below runs in two columns: on the left, what you do and see; on the right, what the software does at the same moment. Use the switch above to see the right-hand column as it is in the local prototype and as it would be once deployed.

Awaiting sign-off. Nothing is built yet.

How the pieces fit

The browser screen and the backend are separate programs that only talk through a JSON interface. Every module plugs into the same small core, and all storage goes through one interface so the database can change later without touching module code.

Build order and what "done" means

Each step is a separate Git branch. A step is finished when you can run its demo, not when the code exists.

Add an action item by typing

The line is "call plumber Friday". It is typed on Saturday 24 Oct 2026, so Friday means 30 Oct.

What you do and seeWhat happens underneath
1
You see

You open the app. Today is the first screen, with one input at the bottom.

Tell me anything…
Underneath

Web appGET /api/today returns what is due or overdue. The input takes focus automatically.

The backend serves the page from the laptop. A phone on the same Wi-Fi opens it over plain HTTP, which is enough to judge layout but not to install it.

The page is served over HTTPS and cached by a service worker, so it opens instantly. A sign-in session is checked first.

2
You see

You type one line and press Enter. There is nothing else to fill in.

call plumber Friday
Underneath

CorePOST /api/messages with the text, device and time zone.

The raw line is written to message_log before anything else, so it is never lost. The input is free for the next line immediately.

3
You see

A moment later a short card confirms what was understood.

Action item addedCall plumber · due Fri 30 Oct
UndoEdit
Underneath

Agent routerSimple lines like "done plumber" are matched by rules with no model call. Anything else makes one request to a small Claude model with today's date and weekday, your time zone, and a compact tool list gathered from every module. The list sits first so prompt caching can reuse it, and token counts are logged.

tool: actions.add_item
args: { "title": "Call plumber",
        "due": "2026-10-30" }

Arguments are checked against the tool's schema. Code, not the model, rejects impossible dates.

4
You see

No question is asked. Adding a task to your own list is low risk, so it saves at once. Undo stays available for 30 seconds.

Underneath

Confirm gateThe tool is marked effect = write_local, so it runs immediately and an inverse is stored in undo_log.

Tools marked destructive, external_send or spend would create a pending_confirmation row and wait for an explicit tap.

5
You see

Today now lists "Call plumber" under "Due this week". On Friday it moves up to "Due today".

Underneath

Actions moduleActionsService.add() inserts into action_item through the storage interface.

StorageOne INSERT into the SQLite file.One INSERT into the hosted database, and the phone's copy updates on its next sync.

Today is built by calling each module's today() and merging the results.

6
You see

If the AI cannot be reached, the line is still saved as a plain item, marked "needs review". You never lose a capture.

Underneath

FallbackAfter an 8 second timeout the router saves actions.add_item with the raw text as the title and needs_review = true.

With no signal on the phone, the web app queues the message locally and sends it when the connection returns.

What changes once deployed

  • HTTPS and a sign-in, so only you can reach the API.
  • The model key moves from .env to the host's secret store.
  • Offline capture on the phone, with sync back to the main copy.
  • Time zone comes from a saved setting instead of the laptop clock.

Add a contact from a free-form note

You paste whatever you remember. The agent sorts it into fields and sets a birthday reminder.

What you do and seeWhat happens underneath
1
You see

You type or paste a note about someone you just met.

Met Priya at Dave's party. Anil's sister. Loves mezcal. Birthday 14 March. Works at Stripe.
Underneath

CoreSame entry point as any message: POST /api/messages. The raw note is saved to message_log.

2
You see

The app checks whether Priya or Anil already exist, so you do not end up with duplicates.

Underneath

Agent routerThe model chooses the contacts tools. It first calls crm.find_contact("Priya") and crm.find_contact("Anil") (effect read), then the write tool. The loop allows up to 3 calls per message.

Matching is fuzzy on name. A close match is shown to you instead of being merged silently.

4
You see

The card says a reminder is set for two weeks before the birthday: 28 Feb.

Underneath

CoreA reminder row is created with the rule "14 days before, every year". The next fire date is computed in code, including 29 Feb birthdays in non-leap years.

5
You see

On 28 Feb, opening the app shows "Priya's birthday in 14 days" on Today, next to her saved gift ideas.

On 28 Feb your phone buzzes: "Priya's birthday in 14 days". Tapping it opens Today with her gift ideas.

Underneath

SchedulerAPScheduler runs inside the backend while it is running. Today also recomputes due reminders every time it loads, so nothing is missed if the laptop was closed.

SchedulerThe server runs the same job around the clock and sends a Web Push (or the chosen channel) to the phone. Missed jobs are caught up at startup.

6
You see

Later, on the laptop, a contacts table lets you search, sort, fix many rows at once and merge duplicates.

Underneath

Laptop layoutGET /api/crm/contacts?q=… and PATCH for bulk edits. The same API as the phone layout, with a wider screen built on top of it.

What changes once deployed

  • Contact details are personal, so the database needs backups and encryption at rest.
  • Reminders are pushed to the phone instead of waiting for you to open the app.
  • Edits made on the phone and the laptop need a sync rule for conflicts.

The morning summary

Set for 07:30. In the prototype you pull it; once deployed, it comes to you.

What you do and seeWhat happens underneath
1
You see

You open the app. The brief for today is the top card on Today.

At 07:30 a notification arrives on your phone: "Your day: 3 things due, 1 streak at risk."

Underneath

SchedulerA 07:30 job runs while the backend is running. If today's brief is missing when you open Today, it is built at that moment.

SchedulerA server job at 07:30 builds the brief and sends a Web Push (other channels to be compared). The service worker opens /today when you tap it.

2
You see

Nothing to do. The app is gathering what matters today from every module.

Underneath

CoreCalls each module's today(ctx) and reminders(ctx, 14 days):

actions due or overdue · habits not yet checked in and streaks at risk · birthdays within 14 days · home tasks due within 7 days. Phase 2 and 3 add emails to answer and health metrics, with no change to the core.

3
You see

A short, readable paragraph, not a data dump.

Underneath

TemplateBy default a fixed template renders the list, with no model call and no tokens used.

LLMOptional, switched on in settings: the structured list (not the raw database) goes to the model to write 4 to 6 plain lines. If the call fails, the template is used.

The result is stored in brief(date, text, data_json), so reopening is instant and free.

4
You see
Good morning. Three things today. Call plumber (due today) · Renew car insurance in 6 days · Meditate: 12-day streak, not yet today. Coming up: Priya's birthday in 14 days.
✓ Call plumber✓ Meditate
Underneath

Web appRendered from GET /api/brief/today. The check-off buttons call the owning module's own API, for example POST /api/habits/{id}/checkins, so the brief is a view and not a second copy of the data.

What changes once deployed

  • Push notifications need HTTPS and a stored subscription from the phone. Neither exists in the prototype.
  • The scheduler runs on a server that stays on, so the brief exists before you wake up.
  • Notification channel (Web Push, a chat bot, email) is chosen at the deploy gate.

Emails to respond to (phase 2)

Read-only first. The app points at mail that needs you and never sends anything. Drafting comes later and still never sends.

What you do and seeWhat happens underneath
1
You see

Once, you tap "Connect Gmail". Google shows a screen saying the app can view your email, and nothing more.

Underneath

Email moduleOAuth 2.0 authorization-code flow with PKCE, scope gmail.readonly. The refresh token is stored outside the repo.

Redirect address is http://localhost. A personal Google app in testing mode may expire tokens after about 7 days. To be checked at phase 2.

Redirect address is the real HTTPS domain. The token goes in the host's secret store.

2
You see

Each morning the app looks through recent mail from real people, skipping promotions.

Underneath

Email moduleGmail API threads.list with a query such as in:inbox newer_than:3d -category:promotions, then metadata only: sender, subject, snippet, who wrote last.

3
You see

Mail that probably needs your reply is picked out, each with a reason.

Underneath

LLMOnly sender, subject and snippet are sent to the model, with a rubric: does this need a personal reply? Output: {needs_reply, reason, urgency}. Sender allow and block lists apply first.

Results go to email_triage. Full message bodies are not stored.

4
You see
Emails to answer (2) Sam Okafor · "Saturday plans?" · asked you a direct question
Open in GmailSnoozeNot neededMake action item
Underneath

Web appShown on Today through the email module's today(). "Open in Gmail" is a deep link to the thread. "Make action item" asks the registry for actions.add_item and does not write to another module's tables.

5
You see

Later still, "Draft reply" puts a draft in Gmail. You read it, edit it and send it yourself from Gmail.

Underneath

GateNeeds a separate, narrower permission and calls only drafts.create. No send tool is registered, so the agent has nothing to call even if asked. A test fails the build if the module references a send call.

What changes once deployed

  • Sign-in redirect and token storage move to the hosted setup.
  • The morning check runs on the server, so triage is ready when the brief is built.
  • Google's rules for read-only mail access in personal apps are re-checked before relying on it.
